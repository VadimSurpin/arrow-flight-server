# Data collection plan for the optimization-choice classifier

Status: plan, nothing collected yet. Written 2026-10-28.

## 1. What we want to learn

For a query on some data, pick the per-query settings that make the Flight path fastest without hurting correctness. Today these are hand-picked from 22 TPC-H queries, and the last two rounds showed how fragile that is:

- `reuseBroadcastOnly=true` was good at a 256 MB broadcast threshold and cost Q9 about 80 s at 10 MB.
- A 256 MB threshold fixed some joins and caused broadcast out-of-memory errors on Q14 and Q21.
- Complete aggregation turns Q18 from 105 s into 52 s and is neutral elsewhere.

TPC-H alone cannot train anything general: 22 queries, one schema, keys sorted the same way. This plan lists what to collect so that a model (or just a set of rules) can be validated on queries and data it has not seen.

## 2. Decisions the model would make (labels)

Only settings that cannot change results. Each row is one knob, with the values to try.

| Knob | Values | Applied at |
|---|---|---|
| `spark.flight.retainPushedFilters` | auto, false | scan |
| `spark.flight.runtimeFilterMinRows` | 0, 50M | scan |
| `spark.flight.runtimeBloomMinKeys` | 1000, off | scan |
| `spark.flight.completeAggregation` | true, false | scan |
| `spark.sql.autoBroadcastJoinThreshold` | 10, 64, 256 MB | session |
| `…dynamicPartitionPruning.reuseBroadcastOnly` | false, true | session |
| `spark.sql.adaptive.enabled` | managed by `FlightAqeGuard` | session |
| `spark.sql.shuffle.partitions` | 48, 96, 192 | session |
| StarRocks: `flight.aggregation_pushdown`, `flight.join_key_reduction`, `flight.complete_aggregation` | on, off | catalog |

Label per query and data layout: the configuration with the lowest median wall time, or `default` when nothing beats the default by more than 5%. Secondary label: core-seconds (the harness already records them).

Not searched as a full grid. Use the default plus one-factor-at-a-time changes, then pairwise runs only for knobs that interact (broadcast threshold × reuse × AQE, retention × runtime filters). That is about 12 configurations per query.

## 3. Features (inputs)

All available before the query runs.

- **Plan shape** (from `/run?explain=1`): number of scans, joins by type, aggregates, distincts, sorts, windows, subqueries, limit; depth of the join tree; whether a join side is an aggregate.
- **Per scan:** row count, file count, bytes, selectivity estimate of the pushed filters (`FilterSelectivity`), number of columns read.
- **Per join:** estimated build and probe rows, key NDV, key `separableGroups`, whether the key is a group-by key above the join.
- **Per grouping column:** NDV, `separableGroups` (already served by the statistics endpoint), type.
- **Data layout:** sortedness of the key within and across files, file size distribution, min/max overlap between files (the same information as `separableGroups`).
- **Cluster:** executor cores, memory per executor, driver heap, Flight server count, measured MinIO read bandwidth.

## 4. Workloads

| Suite | Why it adds signal | Size |
|---|---|---|
| TPC-H SF100 (have it) | baseline, 22 queries | 0 GB new |
| TPC-H SF10 and SF300 | same queries, different size ratios against the 10/64/256 MB thresholds | 10 + 300 GB |
| TPC-DS SF100 | 99 queries, snowflake schema, many small dimensions, multi-fact joins, window functions, rollups. Biggest source of new plan shapes. | ~100 GB |
| SSB SF100 | star schema with a denormalized fact, 13 queries, selective filters | ~60 GB |
| ClickBench (`hits`, 100M rows) | single wide table, string-heavy group-bys, high-cardinality keys, 43 queries | ~15 GB |
| JOB on IMDB | real skewed keys, 4–17 way joins, wrong estimates | ~10 GB |
| NYC taxi (year range) | real data, time-clustered, skewed group-bys | ~20 GB |
| Synthetic generator | controlled axes (below) | any |

MinIO has 886 GB free on its node, so all of this fits.

### Synthetic generator

One table family with the axes we cannot get from the benchmarks:

- key cardinality (10 to 10^9), Zipf skew (0, 0.8, 1.2)
- clustering of the key across files: fully sorted, partially overlapping, random (this is what decides complete aggregation and DPP)
- file count and size (8 MB to 1 GB)
- null fraction of the grouping column
- string versus numeric keys
- selectivity of the filter (0.01% to 50%)

Query templates over it: filter + group-by, join on key with selective dimension, join with aggregate on the same key, top-N, distinct count. Generated by a script, one row per (axis values × template).

### Layout variants

The same TPC-H and TPC-DS data written in three layouts: as generated, sorted by the largest fact table's join key, and shuffled randomly. Layout changes `separableGroups` and filter pruning without changing the logical query, which is the cleanest way to teach the model that data matters.

### Query variants

TPC-DS and TPC-H come with `qgen`/`dsqgen` parameter substitution. Generate 5 parameter seeds per template. For the synthetic suite vary selectivity directly. That makes roughly 1,500 distinct (query, data) points before configurations.

## 5. Budget

Screening: ~1,500 points × 12 configurations × 2 repetitions × ~40 s average ≈ 270 hours. That is too much for one cluster. Cut it down:

1. **Phase 1:** TPC-DS 99 queries × 3 layouts × 12 configurations × 2 reps ≈ 40 h, with a 300 s timeout.
2. **Phase 2:** synthetic suite (cheap, mostly under 20 s) ≈ 30 h.
3. **Phase 3:** SSB, ClickBench, JOB, taxi, with default plus the 4 most influential knobs found in phase 1 ≈ 30 h.
4. **Phase 4:** parameter seeds and TPC-H SF10/SF300, only for queries where phase 1 found a non-default winner.

Early stopping: after one run per configuration, drop configurations that are more than 2× slower than the default and rerun the rest.

## 6. Harness changes

Extend `benchmarks/tpch-k8s/spark_resources.py`:

1. `--suite NAME --layout NAME --config-set FILE` with queries loaded from `queries/<suite>/`.
2. Output JSONL, one record per run:
   `{suite, query, seed, layout, config, mode, rep, wall, error, result_hash, cpu_s, mem_gbs, rx_gb, conn_peak, features{…}, cluster{nodes_ready, pod_restarts, image_digests}, ts}`.
3. Features captured once per (query, layout) from `explain=1` and the statistics endpoint.
4. **Result hash** of the sorted result for every run; a configuration whose hash differs from the default is flagged as a bug, not a label.
5. **Validity flags:** a run is dropped from training if any node was NotReady, a pod restarted, or an error mentions memory or connection resets during the run. Today such runs corrupted v8 and the first v9 attempt.
6. Randomized order of configurations within a query, one warm-up run per query that is discarded.
7. Pin image digests in the record. The v6 to v11 comparison is already hard to read because the server image was `latest` throughout.

## 7. Using the data

1. **Rules first.** Fit a depth-3 decision tree per knob on phase 1 and read it. If the tree reduces to "broadcast threshold by build-side size" or "complete aggregation when `separableGroups > 1`", write it as a cost rule and skip the model.
2. **Model if rules are not enough.** Gradient-boosted trees or a small decision tree compiled to Java, one per knob, predicting the label. Inference cost must be microseconds because it runs at planning time.
3. **Splits.** Leave-one-suite-out and leave-one-template-out. Random splits would leak, because variants of one template look alike.
4. **Metrics.** Regret against the per-query oracle and against the default, plus the share of queries more than 5% worse than the default. Ship only if that share is under 2% on unseen suites.
5. **Guardrails.** Default when the model's confidence is low, a session setting to switch it off, and a log line per decision with the features used.

## 8. Open items before starting

- The DuckDB `tpcds` extension is not installed here; generating TPC-DS needs network access to install it, or a prebuilt `dsdgen`. To be checked.
- No Spark SQL versions of the TPC-DS queries are in the repo; the standard templates need small dialect edits (interval syntax, `rollup`).
- Decide whether StarRocks runs are part of phase 1 or follow once the Spark side is stable. The FE rules are tested, but the BE cannot be built here.
- Fix the unexplained v6 to v11 Flight slowdown first (see section "Baseline" in the next report). Training on a drifting baseline would teach the model noise.
